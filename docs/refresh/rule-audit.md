# FSharpAssay rule audit

The refresh retains the complete M3 partition: 35 experimental, 36 prototype and 22 dummy entries. None becomes a blocking or advisory admission. The machine inventory in `rule-audit.json` maps all 93 identities to their implementation class, existing rule page and review disposition.

## Findings that affect interpretation

`FSA-SEC09` is not a vulnerability scanner. `ProjectParser.fs` compares package names against three placeholder strings, then attempts a zero-range diagnostic that `mkLocated` discards. It neither reads resolved transitive lock identities nor consults a vulnerability database. Its catalogue `Implemented` label describes inherited source, not usable vulnerability evidence. SecurityAssay supplies a separate declared-input dependency assessment with pinned scanners and database freshness.

`FSA-SEC08` checks selected endpoint attributes; `FSA-SEC11` searches bounded ONDC-related text/types and signing names; `FSA-SEC12` searches selected logging expressions for sensitive-looking words; graph `FSA-SEC13` observes a selected HTTP/layer pattern. None establishes complete authorization, message-signature validation, privacy protection or SSRF prevention. Future admission needs actual trust-boundary specimens and application tests.

`FSA-C05` projects compiler diagnostic FS0025. The compiler owns pattern-match completeness; a wildcard hiding a future DU alternative needs separate review. Compiler errors and missing typed trees remain incomplete evidence.

`FSA-C02` recognizes selected partial option operations. Its inherited message overstates guard awareness. Pattern matching and explicit error outcomes are safer recommendations, but caller control flow and framework context determine a justified repair. `Option.get None` raises an argument exception; it is not a general null-reference detector.

Profile attributes and `SuppressMessage` currently affect experimental observations. Their presence never establishes an authority exemption. Explicit configured boundaries now override source profile attributes within the selected declaration context; strict policy exceptions and baseline records retain their separate meanings. Namespace matching uses compiler symbol identity, project matching uses only declared evaluated identities, and exclusions match path segments/globs instead of arbitrary substrings.

Test-file names, property attributes, assertion counts and commit order are style observations. A useful test can contain several related assertions. Classes, objects, interop and measured local mutation are legitimate F# tools. Broad catalogue prohibitions remain unadmitted and should not trigger automatic rewrites.
